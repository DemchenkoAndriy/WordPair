# Архітектура WordPair

> Мікро-тренажер словникових пар. Мета — зайняти ті самі 30–60 секунд, які зараз
> забирає скрол коротких відео, і повернути з них знання замість втоми.

## 1. Продуктові вимоги, що визначили архітектуру

Кожне технічне рішення нижче виводиться з однієї з цих чотирьох вимог.

| # | Вимога | Наслідок для архітектури |
|---|---|---|
| В1 | **Швидкий запуск, мінімум кліків** | Запуск застосунку = початок тренування. Нуль екранів-прокладок, нуль авторизації, синхронний boot-snapshot, PWA з precache |
| В2 | **Дофамінові ефекти** | Окремий шар нагород, керований подіями домену; змінний коефіцієнт підкріплення (криті) закладений у формулу XP |
| В3 | **Кілька механік: спершу пари, далі клавіатура** | Рушії вправ за спільним контрактом; усі дають однаковий потік `Attempt`, тому решта системи не залежить від механіки |
| В4 | **Показники прогресу** | Три горизонти прогресу (раунд / колода / профіль) як окремі чисті функції над одними й тими самими даними |

## 2. Шари

```
┌──────────────────────────────────────────────────────────────┐
│  screens/ + ui/          React: екрани, компоненти, ефекти    │  ← знає про DOM
├──────────────────────────────────────────────────────────────┤
│  state/                  zustand-стор: оркестрація сценаріїв  │
├──────────────────────────────────────────────────────────────┤
│  domain/                 ЧИСТИЙ TypeScript: правила навчання  │  ← не знає ні про що
├──────────────────────────────────────────────────────────────┤
│  data/                   репозиторії, IndexedDB, контент      │  ← знає про сховище
└──────────────────────────────────────────────────────────────┘
```

**Головне правило:** `domain/` не імпортує нічого з React, DOM чи сховища. Він приймає дані
й повертає дані. Завдяки цьому правила навчання вкриті тестами без жодного моку
(40 тестів, ~0.7 с) і переживуть переписування UI чи переїзд на нативний клієнт.

### Що де лежить

| Каталог | Відповідальність | Приклади |
|---|---|---|
| `src/domain/` | Правила навчання | `scheduler.ts` (інтервальні повторення), `scoring.ts` (XP, комбо, рівні), `streak.ts`, `selection.ts` (підбір карток на раунд), `session.ts` (пайплайн спроб) |
| `src/domain/engine/` | Механіки вправ | `types.ts` (контракт), `pairMatch.ts` (механіка №1), `registry.ts` |
| `src/data/` | Персистентність і контент | `repository.ts` (інтерфейси), `idbRepository.ts`, `decks.ts` (лінивий реєстр), `deckSchema.ts` (валідація), `bootSnapshot.ts` |
| `src/state/` | Оркестрація | `store.ts` — єдиний стор, що зшиває рушій, домен і сховище |
| `src/ui/effects/` | Дофаміновий шар | `rewards.ts` (подія → відчуття), `sfx.ts` (WebAudio), `haptics.ts` (вібрація), `speech.ts` (озвучення) |
| `src/screens/` | Екрани | `SessionScreen`, `ResultScreen`, `DecksScreen`, `StatsScreen`, `SettingsScreen` |
| `src/content/decks/` | Контент | `vscode-ui.json`, `vscode.json`, `sap-b1.json`, `jira.json` |

## 3. Потік даних одного тапу

```
   тап по плитці
        │
        ▼
  pairMatchEngine.submit()        ← чиста функція: (стан, ввід, час) → (стан, Attempt[], feedback)
        │
        ├── Attempt[] ──► applyAttempt()          ← нарахування XP, комбо, рівень
        │                     ├──► schedule()      ← новий інтервал повторення картки
        │                     └──► RewardEvent[]   ← «що сталося», без слова про звук
        │
        ├── feedback ──► анімація плиток (CSS)
        │
        └── RewardEvent[] ──► playReward() ──► вібрація + WebAudio + банер
                                   │
                                   └──► запис у IndexedDB (пачкою, через 400 мс, поза кадром)
```

Ключове: **запис у сховище ніколи не блокує кадр**. Джерело правди під час раунду —
пам'ять; IndexedDB отримує накопичену пачку із затримкою. Анімація на 60 fps важливіша
за миттєву консистентність, бо втрата останніх 400 мс прогресу при аварійному закритті
коштує дешевше, ніж підвисання на кожному тапі.

## 4. Рішення й обґрунтування

### Р1. Механіки як змінні рушії за спільним контрактом (В3)

```ts
interface RoundEngine<TState, TInput> {
  init(input: RoundInit): TState
  submit(state: TState, input: TInput, at: number): RoundStep<TState>
  isComplete(state: TState): boolean
}
```

Кожен рушій на виході дає `Attempt { cardId, correct, latencyMs }` — і більше нічого.
Планувальник повторень, XP, статистика, стріки й ефекти написані **один раз** проти
цього типу. Додати «написання з клавіатури» = написати `typing.ts` і додати рядок
у `registry.ts`; жоден інший файл не змінюється.

Стан раунду плоский і серіалізовний — сесію можна відновити після згортання застосунку.

### Р1a. Конвеєр: поле не спорожнюється

Плитка — це **слот**, який живе весь раунд; картки в ньому змінюються. Зійшла пара —
обидві плитки сіріють і гаснуть, але місце тримають, доки не прийде підміна.
Сесія від цього триває скільки завгодно, а поле ніколи не порожніє.

Підміна винесена в окремий інтерфейс `RefillableEngine` (`canSweep` / `sweep` / `refill`):
режим «написання з клавіатури» цього не потребує і не має тягнути зайвих методів.
Затримка перед підміною живе в UI, а не в домені — це питання анімації, а не правил гри.

**Чому підміна пачкою, а не по одній парі.** Якщо міняти одразу після кожного збігу,
нова пара займе рівно ті два слоти, які щойно звільнилися, — і її можна вгадати,
взагалі не знаючи слова. Тому `SWEEP_BATCH = 2`: підміна чекає на дві зійшлі пари
й розкидає нові картки по звільнених слотах **незалежно в кожній колонці**.
Позиція перестає бути підказкою. Виняток — коли черга майже порожня: чекати нема
на що, і поле просто стискається.

### Р1b. Безкінечний режим

Ціль раунду — `target: number | null`. `null` означає, що раунд не завершується сам:
`isComplete` завжди false, а стор доливає чергу картками, яких зараз немає на полі.
Завершує користувач кнопкою — і сесія записується так само, як скінченна.
Жодної окремої гілки в нарахуванні XP чи в планувальнику повторень це не потребує.

### Р2. Локальне сховище, без акаунтів (В1)

Авторизація коштує щонайменше три кліки й мережевий запит на старті — це прямо
суперечить головній вимозі. Тому: усе локально, IndexedDB через `idb`.

Шар `ProgressRepository` — інтерфейс. Синхронізацію з сервером згодом можна додати
як другу реалізацію (або декоратор із чергою) без правок у домені та UI.

### Р3. Boot-snapshot у localStorage (В1)

IndexedDB асинхронна: читання з неї коштує кадр-два, і це видно як блимання порожнього
екрана. Тому мінімум для першого кадру — яка колода, який режим, рівень, стрік —
дублюється в `localStorage` і читається **синхронно до першого рендера**.
Повний стан підвантажується з IDB вже під анімацію появи.

Заміряно на зібраному білді: **перша інтерактивна плитка — 401 мс, нуль кліків**.

### Р4. Дофамін як окремий шар (В2)

Домен породжує події (`hit`, `combo-milestone`, `level-up`, `deck-mastered`…) і не знає
про звук чи вібрацію. `ui/effects/rewards.ts` — єдине місце, де подія стає відчуттям.
Дизайнер може переробити всі ефекти, не торкаючись логіки навчання; і навпаки.

Що саме дає «затягування»:

| Механізм | Реалізація |
|---|---|
| Змінний коефіцієнт підкріплення | «Критичний удар» ×2 XP з імовірністю 12% — головний важіль стрічки тіктоку |
| Наростання | Комбо-множник до ×2 + висота ноти росте з комбо (пентатоніка — будь-яка послідовність звучить приємно) |
| Миттєвий відгук | Вібрація 12 мс + звук на кожному влучанні, < 50 мс від тапу |
| Близька ціль | Смужка XP до наступного рівня завжди на екрані; перші рівні беруться за одну-дві сесії |
| Втрата | Комбо обнуляється на помилці — це те, що змушує бути уважним |
| Продовження в один тап | На екрані підсумку головна кнопка одна: «Ще раунд» |

Звук синтезується WebAudio, а не вантажиться файлами: нуль байтів у бандлі,
нуль затримки на першому звуці, і висоту тону можна змінювати динамічно.

Усі ефекти вимикаються в налаштуваннях і автоматично приглушуються при
`prefers-reduced-motion`.

### Р4a. Озвучення — властивість колоди, а не глобальний перемикач

Тап по плитці вимовляє слово через `speechSynthesis`: системні голоси, нуль байтів
у бандлі, працює офлайн, без ключа й без мережі — єдиний варіант, що не суперечить
локальності застосунку.

Що саме озвучувати — вирішує колода:

```ts
speech?: { side: 'prompt' | 'answer'; lang: string }
```

Без цього поля колода мовчить. Це не формальність: у колоді гарячих клавіш
англійський бік — це `Ctrl+Shift+P`, вимовляти його безглуздо, а в SAP-колоді
англійського немає взагалі. Поле проходить ту саму валідацію на межі, що й решта
контенту (`deckSchema.ts`), і вкрите тестами.

Виклик іде **прямо з обробника дотику**, а не з ефекту після оновлення стану:
на iOS `speechSynthesis` поза жестом користувача мовчки ігнорується.
Кнопка 🔇 у шапці глушить і озвучення теж.

### Р5. Три горизонти прогресу (В4)

| Горизонт | Що показує | Де |
|---|---|---|
| Раунд | Смужка `закрито/ціль` (або `∞ · N`), лічильник комбо | Шапка екрана тренування |
| Колода | Вивчено / у роботі / нових + смужка засвоєння | Екран підсумку, список колод |
| Профіль | Рівень і XP, стрік днів, точність, рекорд комбо, час | Шапка (завжди) + екран «Прогрес» |

Усі три — чисті функції над тими самими `CardProgress` і `SessionRecord`
(`deckMastery()`, `levelProgress()`, `touchStreak()`), тому не можуть розійтися між собою.

### Р6. Інтервальні повторення: Ляйтнер, а не FSRS

П'ять боксів з інтервалами 10 хв → 1 д → 3 д → 7 д → 21 д, плюс м'який `ease`-множник
у стилі SM-2. Помилка відкидає на один бокс назад (не в нуль — щоб не знецінювати
попередню роботу).

Свідомо простий вибір: мікро-сесії по 30–60 секунд не переживуть «важкого» FSRS,
а користувачу потрібне відчуття руху, а не аптечна точність інтервалів. Алгоритм
ізольований в одному файлі — замінити можна будь-коли.

Підбір карток на раунд: ~60% прострочених повторень + ~40% нових, з добором,
якщо чогось бракує. Раунд ніколи не буває порожнім. У безкінечному режимі той самий
підбір працює й на доливання черги — з виключенням карток, які зараз на полі,
щоб одне слово не з'явилося двічі одночасно.

### Р7. Контент — дані, а не код

Колода — JSON із власною версією. Легкий каталог (`DECK_CATALOG`) у першому чанку,
самі картки — окремі чанки через `import()`. Холодний старт не тягне 20 колод,
коли користувач відкриє одну.

Кожен JSON проходить `parseDeck()` на межі системи: колоди — зовнішні дані
(згодом і імпорт користувача, і завантаження з мережі), тому вони заходять як
`unknown` і перевіряються, а не приводяться типом.

## 5. Технології

| Вибір | Чому |
|---|---|
| React 19 + TypeScript + Vite | Стандарт, швидка збірка, `strict` + `noUncheckedIndexedAccess` |
| zustand | Стор без провайдерів і бойлерплейту; ~1 КБ |
| `idb` | Тонка обгортка над IndexedDB, ~2 КБ |
| vite-plugin-pwa | Офлайн і встановлення на домашній екран — обов'язкове для В1 |
| Власний CSS | Жодної UI-бібліотеки: кожні 30 КБ бандлу — це затримка старту |
| vitest | Тести домену без DOM |

**Бандл на сьогодні: 70 КБ gzip основний чанк + 1–2 КБ на колоду.**

Свідомо НЕ взято: роутер (навігація — стан, а не URL; посилання на екрани не потрібні),
анімаційна бібліотека (CSS-keyframes вистачає), UI-кіт, бекенд.

## 6. Межі системи

```
Користувач ──tap──► React ──► store ──► domain (чистий) ──► RewardEvent
                       │                    │
                       │                    └──► CardProgress ──► IndexedDB
                       └──► effects: WebAudio · Vibration API · CSS
```

Зовнішні залежності рантайму: **немає**. Застосунок повністю працює офлайн.

## 7. Що навмисно відкладено

- **Синхронізація між пристроями** — інтерфейс репозиторію вже готовий до другої реалізації; вмикати варто тоді, коли з'явиться реальний запит, бо це тягне акаунти, а акаунти тягнуть кліки на старті.
- **Редактор колод у застосунку** — поки колоди редагуються як JSON у репозиторії.
- **Режим «написання з клавіатури»** — контракт рушія готовий, реалізація в наступній фазі.
- **Сповіщення про стрік** — потребує дозволу, а дозвіл — це діалог на старті.

## 8. Перевірка

```bash
npm run test    # 40 тестів домену
npm run build   # tsc -b + vite build
npm run dev
```

Наскрізний прогін у Chromium (390×844) підтвердив: старт без кліків, повний раунд
із п'яти пар, екран підсумку з XP / точністю / комбо / рівнем, нуль помилок у консолі.
